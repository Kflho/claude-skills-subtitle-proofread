# ADR-008: Qwen3-ASR 长音频必须自己分块（60s + 补零时长）

- **Date**: 2026-10-18
- **Status**: 🟡 Accepted
- **Context**: P2 真实验证用莎莉 EP001（1966 年动画，25.2 分钟，单声道对白 + BGM + OP/ED）跑
  `qwen_asr` 的 `transcribe(return_time_stamps=True)`。结果不可用：

  - token 时间轴 48.2% 为零时长（`start == end`），段级 SRT 出现 120s 长段和大量 0s 段；
  - 多个 10–45s 的空洞，整集约 5 分钟没有任何 token；
  - 处理时间 1252.8s（RTF 0.83），远超方案估计的 0.08–0.15。

  分长度切片复现（同一音源 300s 起）：

  | 输入长度 | 零时长 token | token 时长中位数 | 文本 |
  |---:|---:|---:|---|
  | 60s | 17.6% | 0.107s | 通顺可读 |
  | 90s | 34.7% | 0.080s | 基本可读 |
  | 120s | 54.6% | 0.000s | 开始出现明显错词 |
  | 180s | 56.8% | 0.000s | 错词更多 |

  结论：`qwen_asr` 内部按 180s 分块（`MAX_FORCE_ALIGN_INPUT_SECONDS`）在这类素材上会让
  ForcedAligner 把大段文本压到 chunk 末尾，同时拖慢整体推理。

## Decision

1. **worker 自己分块**（`scripts/asr/qwen3_worker.py`）：`--chunk-sec` 默认 **60**，用
   `qwen_asr.inference.utils.split_audio_into_chunks` 的低能量边界切；每个 chunk 单独
   `transcribe(return_time_stamps=True)`，token 时间加 `offset` 后合并。`--chunk-sec 0` 可关。
2. **补零时长 token**：合并后对连续 `start == end` 的 run，在「前一个 token 的 end」与
   「后一个 token 的 start」之间等分——仅当这段间隔 ≤ `max(3s, 0.6s × token 数)`。
   长音乐/静音段保持原样，不用文本去填。
3. **不切默认模型**：1.7B 仍是默认；0.6B 在实测里没有更快（见下），质量也更差。
4. **默认管线继续走 Whisper**：本次验证只用于修订方案，不改 `run_all` 默认。

## Evidence after the change（莎莉 EP001，3080 Ti Laptop 16GB）

| 指标 | 内部 180s 分块 | 自切 60s | 自切 60s + 补零（终版） |
|---|---:|---:|---:|
| 处理时间 | 1252.8s | 446.8s | **312.9s** |
| RTF（含加载） | 0.829 | 0.295 | **0.207** |
| 零时长 token | 48.2% | 27.1% | **8.4%** |
| token 时间轴联合覆盖 | — | 47.9% | **59.6%** |
| 字幕 cue 覆盖率（均值） | 0.361 | 0.570 | **0.717** |
| cue 覆盖率 ≤0.2 占比 | 45.8% | 16.9% | **10.6%** |

> 终版 cue 覆盖 median 0.805、≥0.8 占 51.2%；OP/正片/ED 分别 0.515 / 0.720 / 0.860。
> 两次整集运行 312.9–446.8s（RTF 0.207–0.295），差异来自散热/功耗，排期按慢值算。

对照：Whisper large-v3 q5（`whisper-cli`，RTF 0.184，5361 字符 / 369 段）。
Qwen3-1.7B 与 Whisper 的逐段字符一致度 mean 0.505 / median 0.585（两引擎差异很大，
说明单引擎自动替换文本风险高，双引擎/glossary 策略仍然必要）。

> Whisper 的 cue 覆盖率 0.953 不能当作「语音检测更好」：whisper.cpp 的 segment 是连续平铺，
> 天然覆盖整段音频；Qwen token 只覆盖 FA 认为有字的位置。两者不可直接比。

**速度对照（120s 切片，模型热态）**：

| 模型 | 单次 120s 推理 | RTF |
|---|---:|---:|
| Qwen3-ASR-0.6B + FA | 14.7s | 0.122 |
| Qwen3-ASR-1.7B + FA | 22.0s | 0.183 |

但整集实测 **0.6B 用了 880s、1.7B 用了 313–447s**（与热态结论相反）。最可能是连续满载后的
笔记本 GPU 降频；这一点必须在批量前复测，不能直接拿 0.6B 当「快 1.5×」的草稿模型。

## Consequences

- ✅ 时间戳可用性从「大面积塌缩」恢复到「局部零时长」；RTF 降到 0.21–0.30，193 集约
  **17–24 小时**（仍高于方案估计 6–12h，见风险）。
- ✅ 分块逻辑在主进程之外（worker），主环境仍不 import torch；分块参数可配。
- ✅ 补零是保守插值，不修改文本、不虚构语音。
- ⚠️ 60s 仍是经验值：90s 的零时长率翻倍，但边界损失更小；需要金标边界才能定 trade-off。
- ⚠️ 0.6B 热态比 1.7B 快 1.5×（RTF 0.122 vs 0.183），但整集反而慢一倍多（880s vs 313–447s），
  疑为持续满载降频；「0.6B 做草稿」不能靠一次整集数据下结论。质量也更差
  （cue 覆盖 0.504 vs 0.717，OP 0.215 vs 0.515）。
- ⚠️ 整集 RTF 随散热/功耗波动（本次 0.207–0.58），193 集批处理必须按最差情况估时。
- ⚠️ 跨 chunk 切在低能量边界，仍可能切断词；没有 overlap/去重。
- ⚠️ 与 Whisper 的一致度只有 0.5，且没有日语金标，**P50 ≤100ms 仍未验收**。

## Alternatives rejected

| 方案 | 原因 |
|---|---|
| 继续用 qwen_asr 内部 180s 分块 | 实测时间戳塌缩 + 丢文本，且更慢 |
| 分块 180s + 5s overlap | 180s 已经越过可用阈值；overlap 还要处理重复文本 |
| 不分块直接整集 | 25 分钟输入同样塌缩，且无法定位空洞 |
| 用 vLLM 后端提速 | 官方不支持 Windows；本机无 Linux/WSL 环境 |
| 0.6B 顶默认换速度 | 实测更慢且质量更差 |

## Follow-up

- 用人工听校的 100 条 cue 边界验收 P50/P90；再决定 45/60/90s 的最终 chunk 长度。
- chunk 边界 overlap + 文本去重；补零时长的上限继续按金标调。
- 排查 0.6B 反而更慢的原因（相同音频编码器？生成 token 数？）；必要时试 fp16。
- 若 193 集是硬需求：cloud 兜底（MAI/Scribe）或换 GPU 的性价比要重新算。
